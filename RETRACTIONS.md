# Retractions

This file records every published statement in this repository that a later
revision **withdrew or inverted**. A clarification that only adds detail is not
listed here; a statement an implementer could already have built against, and
which is now wrong, is.

The convention exists because this repository's corrections have historically
arrived inside otherwise-routine edits, where a reader who had already
implemented the earlier text had no reason to re-read the section. Each row
names the affected section, and each affected section also carries a one-line
inline note at the point of the change.

## What earns a row

A **reversal**: the specification previously published a statement, and the
current text says something incompatible with it, so an implementation built
faithfully on the old text now produces wrong behaviour. Inverted polarity,
transposed fields, a relocated or re-identified byte, a withdrawn subsystem, a
changed numeric contract, a permission to omit that is now load-bearing, and a
negative claim that turned positive all qualify.

A **clarification** does not earn a row: added detail, a narrowed scope that
leaves the old text still true, a gap being filled for the first time, a
renaming with no behavioural consequence, or a first publication of geometry or
constants the spec had previously declined to state. The bar is deliberately
high. A bloated index with false rows is nearly as bad as no index, because
consumers stop trusting it and re-audit sections that never changed.

Statements published **only in an issue closing comment** and never in spec
prose still earn a row, because issue answers are this project's delivery
channel to the implementation. Those rows name the issue instead of a commit.

## How to use it

1. Note the spec commit your implementation last reconciled against.
2. Read every row at or after that commit in the table below. Rows are in spec
   commit order, oldest first, and the file is append-only, so new rows always
   arrive at the bottom.
3. Re-audit exactly the named sections. Do not re-read the whole document.
4. Treat a passing test as evidence of nothing on those sections. The failure
   mode this index exists for is a test that pins retracted behaviour and keeps
   passing.

Several commits below are work-in-progress snapshots that were finalised by the
repair commit immediately following them. Where the cited commit is a snapshot,
the published form may have landed in its successor:

`552d0c6` -> `2a5c855`, `3b9e8f8` -> `501fa85`.

## Completeness caveat

**This index is a backfill, and it is not proven exhaustive.** It was assembled
in one pass over 192 commits of history by three independent sweeps, each with
known blind spots:

- **Retraction-vocabulary sweep of current prose.** Every occurrence of
  retract / withdraw / supersede / "earlier revision" / "was wrong" in
  `systems/`, `formats/` and `catalogs/` at HEAD (423 hits across 70
  documents), attributed to its introducing commit by `git blame` and read as
  353 distinct paragraphs. This finds reversals that the corrected text was
  honest about. It cannot find a reversal that left no note.
- **Removed-line sweep of the full patch history.** Every line removed across
  all 192 commits that no longer appears at HEAD (3,911 lines), filtered for
  normative absolutes and for polarity vocabulary, then read. This is the sweep
  that found the *silent* reversals, including the `npc-schedules.md` tile-set
  bit polarity and the Frigate hull value. It is a keyword filter, so a short,
  line-wrapped removal using none of those words is unexamined. Six commits
  were excluded from this sweep by filter: `5b816cc`, `e3c6a0e` and `14d7cc0`
  (early wholesale authoring passes), and `cd6b442`, `1222b3d` and `834c33b`
  (provenance-redaction passes assumed semantically neutral). Reversals
  introduced **by** those six against still-earlier text are not covered.
- **Issue sweep.** All 149 issues were keyword-scanned; roughly 45 were read in
  full. An issue-channel reversal phrased without retraction vocabulary — a
  table quietly republished with different values — would be missed. Eighty
  issues were scanned but not read.

Other known gaps: no commit's full diff was read end to end, so a reversal
expressed only as a wholesale paragraph rewrite sharing no vocabulary with its
predecessor would escape all three sweeps. `EXTRACTION.md` was not mined and is
known to still carry at least one retracted name (the LOOKOBJ "Britannia
chunk-map overlay", withdrawn at `474a043`). Rows whose withdrawn text lived
only in a private analysis note, never in published prose or an issue answer,
were deliberately excluded even where the current text says "an earlier
revision"; those notes are self-descriptions of an internal pipeline, not
contracts a consumer could have implemented.

**This index has already failed once, in exactly the way it exists to prevent.**
The mining pass that assembled it verified 425 reversals; the publish step that
produced the first form of this table wrote 230 rows. Part of that shortfall was
legitimate — many rows deliberately bundle several documents that shared one
reversal into a single row, and roughly thirty mined candidates were rejected as
clarifications rather than reversals — but part of it was not. A mechanical diff
of verified reversals against published rows flagged 49 with no apparent row at
all. A reconciliation pass re-checked all 49: 48 were already covered, by a
bundled row or by a row filed under a different section number, and **one was
genuinely omitted** — the issue-#42 dungeon-mode statement, now filed against
`systems/visibility.md` 12.5. None of the 49 was rejected as a clarification and
none was left undetermined. Appending that row brings the table to 231 rows.

Two things follow for a reader. First, the append-only, complete-for-reversals
contract stated at the head of this file is the intent of the file, not a proven
property of it: a section this index does not name has not thereby been cleared,
and at least one confirmed reversal did reach consumers unlisted. Second, the
single omission was one of three retractions carried by a single issue answer,
two of which were filed and the third of which was dropped — so the likeliest
remaining defect has the same shape: a multi-part correction filed for some of
its parts only. When re-auditing against a row that cites an issue, read that
whole issue answer, not only the part the row quotes.

**This index has now failed a second time, in a different way: reversals
retracted *inline* but never indexed.** The consuming engine found it, not us.
It had instructed every one of its audit agents to grep this index as their
single retraction check, on the strength of the "append-only and complete for
reversals" contract at the head of this file. That check was weaker than
presented. A section can carry a plain inline retraction — "any earlier
statement that X is retracted", "that is withdrawn", "**Correction:**" — and
have no row here at all, and an agent grepping only the index never sees it.
The engine named two: `systems/town-mode.md` section 17's poison-gas cadence
bullet, and `systems/blackthorn.md` section 5's withdrawal of the "punishment
animation / dragged-away victim" wording, whose sibling withdrawal in section 4
*was* filed, as R205.

A five-part sweep followed, reading every document in `systems/` (51),
`formats/` (26) and `catalogs/` (9), plus `EXTRACTION.md`, `NEXT-STEPS.md` and
`README.md` — 89 documents — with two or three independent retraction-vocabulary
passes over every line, each hit mapped to its enclosing section and checked
against the Document and Section columns of every row. It found **39 reversals
this index did not usably carry**, now filed as **R233 through R271**:

- **26** had no row anywhere. Two systemic shapes recur. Commit `3c5d72c` had
  zero rows despite its own message declaring "Two corrections to previously
  published text" (R233, R234). And the multi-part-correction failure this
  caveat already predicted happened twice more: R235 is the dropped section-5
  half of the `3d074ae` correction whose other parts are R203, R204, R205 and
  R208, and R247 is the dropped second half of the two-part withdrawal whose
  first half is R074.
- **13** were reversals this index *did* record, but under a document or a
  section number the affected document's own grep could not reach — the whole
  reversal filed against a sibling document (R243, R244, R257, R258, R260,
  R261, R264, R268, R270), against a sibling section (R262, R263), or against
  one half of a paragraph (R259, R267). `formats/shoppe-dat.md` appeared zero
  times in this file before R260. R262 exposes a plain pointer error: R109's
  Section column reads "npc 9" and the retraction is in section 8, which was
  section 8 at R109's own commit too.

Roughly sixty further sites carrying retraction vocabulary were read and
deliberately given **no** row: about half were already covered by an existing
row at the named document and section, and the rest were clarifications,
renamings with no behavioural consequence, or supersessions of readings that
lived only in a private analysis note. Those judgements are recorded in the
sweep, not here, so that this table does not bloat with false rows.

Three limits on that sweep, stated plainly. It was a vocabulary sweep of
current prose, so a **silent** reversal — a paragraph rewritten wholesale with
no note — is outside what it could find; no removed-line diff sweep was run for
it. The issue tracker could not be read from the sweep's workspace, so four
findings (R240 and R253 through R255) rest on the spec's own self-description
that the withdrawn text was delivered, and are filed against the issue rather
than a commit. And section attribution comes from the nearest preceding
heading.

What a reader should take from this: **the index is a necessary check, not a
sufficient one.** Grepping this file for your document tells you which
reversals were *filed* against it. Until every inline retraction in the spec is
also a row — which is now the stated convention in `CLAUDE.md` and `AGENTS.md`,
where an inline-only retraction is named as a bug — a grep of a section's own
prose for retraction vocabulary remains a second check worth running, and the
two together are stronger than either.

If you find a reversal that is not listed, it is a defect in this file. Open an
issue and it will be appended.

## Row identifiers and the audited-through protocol

Every row carries a permanent identifier in the `Row` column, `R001` upward.
**An identifier is never reused and never renumbered**, including if a row is
later found to be wrong: a withdrawn row keeps its id and gains a note saying
so. New rows take the next free number, so the highest id in the file is also
the row count.

Ids exist so a consumer can record a watermark rather than re-reading the
table. The intended loop:

1. Audit the rows you have not yet audited.
2. Record the highest id you covered, for example `audited clean through R231`.
3. On the next pass, read only rows above that id.

The `Spec commit` column is not a safe watermark on its own. Rows are ordered
by the commit that made the change, but a reversal can be discovered and filed
long after the commit that caused it, so a row with an older commit may be
appended below a newer one. Ids are append-ordered and monotonic; commits are
not. Use the id.

Two caveats a consumer should encode rather than assume. A row may be edited in
place to correct its wording without its id changing, so re-reading an
already-audited row is cheap insurance if the file has changed at all. And the
completeness caveat below applies to the whole table: an id watermark tells you
what you have read, not that everything worth reading has been written.
