# Containers and Pickups

## 1. Overview

Ultima V has three ways for the party to obtain loose resources during normal
play:

- `G` Get collects visible pickups, dungeon chests, food/crops, and some
  table objects.
- `O` Open opens unlocked doors and containers, including chests that use a
  container helper after the visible tile check.
- `J` Jimmy unlocks locked containers and doors using key stock, then hands
  successful chest cases into the same container/item machinery.
- `S` Search reveals hidden objects, buried Moonstones, traps, and secret
  features; when it finds a hidden object or Moonstone pickup, the discovered
  object is granted through the same inventory-add path used by pickups and
  chests.

This spec centralizes the container and pickup contract. Door state, floor
changes, and the detailed lockpick rules live in `doors-and-z-transitions.md`;
this document owns what happens once a gettable object or container result is
ready to become inventory.

## 2. Runtime Stores

The pickup system bridges three stores:

- **Shared party inventory.** Gold, food, keys, gems, torches, reagents,
  equipment counts, scrolls, and quest items are counters or flags in the save
  image. `catalogs/item-list.md` names the item families; `formats/saved-gam.md`
  gives the byte layout.
- **Per-map object table.** The active map has an object list whose entries
  carry a tile/category byte, position, floor/depth, and inventory-add code.
  Surface and town pickups search this table before falling back to raw tile
  classification.
- **Saved Moonstone slots.** Buried Moonstones are tracked in the Gate Travel
  slot block in `SAVED.GAM`, not in the static map files. Search can surface a
  matching slot as a temporary "strange rock" pickup, and Get invalidates the
  slot when that pickup is collected.
- **Live map tile buffer.** Some pickups are encoded as mutable terrain or
  furniture cells. Collecting crops, borrowing an object, opening a chest, or
  eating from a table rewrites the live tile byte and marks the visible map
  dirty. These mutations are visit-local unless separately persisted by the
  object layer.

Dungeons differ from surface/town maps: a dungeon chest is identified by the
class nibble of the current dungeon cell. The cell does not store its exact
contents. Contents are generated by the command handler when the chest is
opened or gotten.

Search bridges the same stores through several lookup paths. A matching hidden
object-table entry dispatches through the inventory-add path. If that scan
misses, Search checks for a slot-indexed treasure marker at the searched
coordinate, classifies the live tile to choose a location prefix or hidden-door
mutation, and then runs the saved Moonstone, rare-reagent, and hidden-treasure
tables. Ordinary feature results are narration, while hidden-door reveal,
bomb-trap clearing, chest post-processing, and treasure-like results can mutate
the live tile buffer or grant inventory through their owning helpers.

## 3. G-Get

Get operates on the tile in front of the party in overworld and town-family
scenes.

1. The command runs the shared tile-interaction preflight gate. A failed gate
   exits without changing inventory.
2. The handler computes the adjacent target coordinate from the current
   position plus the cached direction step.
3. It scans the current map object table for a matching position. In normal
   world scenes, floor/depth must also match. The scan uses a narrow pickup
   visual filter: a few special object-tile markers and one contiguous
   loose-object visual family are accepted, while actors, blockers,
   already-handled entries, and unrelated object rows at the same coordinate
   are ignored.
4. On a matching pickup object, the object's separate inventory-add code is
   dispatched, the appropriate inventory counter or flag is updated, and ordinary
   object-table pickups clear the consumed slot through the shared slot
   initializer. Moonstone "strange rock" pickups additionally invalidate the
   associated Gate Travel slot after granting the Moonstone.
5. If no object matches, the handler classifies the live map tile. Known tile
   fallbacks include borrowing table/furniture objects, picking crops, and
   eating from reachable table cells. If no fallback applies, Get prints the
   standard nothing-to-get refusal.

Dungeon Get acts on the underfoot dungeon cell. Door cells refuse until opened.
Chest cells roll generated contents and add every successful category to the
party inventory. Other dungeon cells refuse.

The accepted per-map object filter is visual, not the same byte as the
inventory-add class code. Accepted pickup object tiles are the named special
object markers used for Moonstones and carpets plus the contiguous
loose-object visual family also used by the regalia and shard pickups. After a
visual match, the handler reads the object's inventory-add code and passes that
code to the dispatcher in Section 8. This is how the non-speaking `CASTLE:0`
object slot 31 can carry the Sandalwood Box inventory-add code `0x0E`: the
pickup succeeds because the object's tile is in the gettable visual family, not
because every inventory-add code below `0x10` is itself an accepted object-tile
tag.

## 4. Chests And Containers

Surface/town chests can be reached through Get, Open, Jimmy, or Search depending
on how they are encoded:

- A visible unlocked or closeable container can be opened. The live cell is
  rewritten to the open-container tile, the visible map is marked dirty, and the
  chest helper determines whether the chest is empty, trapped, or grants
  contents.
- A locked container must be Jimmied first. A successful pick clears the
  matched object's lock/trap flag — preserving its content class — so a later
  Open/container helper enters the chest/content path with no trap armed. A
  failed pick breaks one key and changes nothing at all: the lock still stands,
  the contents are intact, and the container can be attempted again while keys
  remain. There is no "broken-lock" state and no way for a failed pick to
  destroy a container's contents. The formulas and key side effects live in
  `doors-and-z-transitions.md`.
- A too-heavy or otherwise non-openable foreground object refuses before the
  chest helper runs. A non-matching fallthrough can still enter the helper and
  produce a "nothing to open", "can't", trap, empty-chest, or content result
  based on per-map object data.
- A hidden container or object may be found by Search through the map object
  table. Search announces the find and dispatches the object's inventory-add
  code.
- A slot-indexed treasure marker may be found by Search through the active
  object table after the hidden-object scan misses. This lookup scans active
  object slots in reverse priority order, so the highest matching slot wins
  when several dynamic records occupy the searched coordinate.
- A hidden door may be revealed by Search when the searched live tile is the
  hidden-door marker. This path prints the hidden-door find, rewrites the live
  target tile to the revealed variant selected by the current plane, and marks
  the map dirty. It does not run the later Moonstone, rare-reagent, or fixed
  hidden-treasure scans.
- A buried Moonstone may be found by Search through the saved Moonstone slot
  block after live-tile classification. Search creates a visible "strange
  rock" pickup for the matching slot; collecting that pickup grants the
  Moonstone and clears that slot's valid destination marker. One live-tile
  marker skips this Moonstone pass and continues with the reagent and fixed
  hidden-treasure scans.
- A fixed hidden treasure may be found by Search through the resident hidden
  treasure table described in Section 5. This path is independent of the active
  object table at lookup time, so it can represent fixed map secrets that are
  not present as ordinary visible object rows. When a record is accepted, Search
  stages a pickup into an active-object slot at the searched coordinate and
  names the staged object; the later Get path owns the inventory transfer.
- A dungeon chest is an underfoot dungeon cell. Its exact contents are not
  stored in `DUNGEON.DAT`; they are generated at interaction time.

Trap handling is part of the chest helper. A trapped chest prints the trap
result, applies the selected damage or status effect through the shared trap
resolver described in `traps.md`, and then either grants contents or leaves the
chest consumed according to the helper result. The helper passes no trap
flavour: the container is trapped or it is not, and `traps.md` owns the flavour
choice. The surface/town chest content pools below use the chest's low
seven-bit class after any trap bit is removed.

The trapped flag and the locked flag are the same flag, so a container that has
been successfully Jimmied is also disarmed and its later Open is trap-free.
Whichever way the chest is entered, the low seven-bit content class survives
every lock and trap interaction, so container contents can never be destroyed
before they are generated.

When the chest helper opens a matching surface/town object-table chest, it
chooses the party member who opens it through the shared acting-member
selection, and it does so *before* testing whether the chest is trapped. A
prompt is only one of that selection's three outcomes — a combat-class scene and
a set active character both bypass it, and a party with exactly one able member
selects that member silently. `systems/traps.md` § 2.1 owns the priority order
and its consequences, including the case where the selection returns nobody and
the command aborts before any trap can fire.

The helper then **clears the matched object record outright** — its kind, its
position, and the byte carrying its lock/trap flag and content class are all
zeroed — marks inventory/status state dirty, and in town-family scenes reduces
the shared moral-standing selector by two units, clamped at zero. Two ordering
details are load-bearing and were re-derived from the shipped binaries on
2026-08-23:

- The clear happens **after** the helper has taken its own local copy of the
  container's flag/class byte and **before** it tests that copy for the trap
  condition. So the trap still fires on this open, and content generation still
  uses the class bits, even though the record no longer exists by then.
- The record lives inside the persisted save image, so the clear is durable. A
  later Open of the same square matches no container and reports that there is
  nothing to open; a trapped surface or town container therefore cannot spring a
  second time. `systems/traps.md` § 4 states the same rule for the trap side and
  records that an earlier revision of that document published this point as an
  open gap on the false premise that the handler only masked the flag in a
  working copy.

If the copied byte's high bit is set, the helper prints the trapped result and
invokes the shared trap-effect resolver in `traps.md` with the selected member as
the target context. The same low seven bits then drive content generation whether
or not the chest was trapped. If no content row from either pool succeeds, the
chest reports empty.

Every successful row from either pool is committed the same way: the engine
acquires a free active-object slot, writes the result family and the rolled
quantity into it, and names the granted object. The slot allocator carries a
shipped quirk that a reimplementation should reproduce rather than tidy away.
It scans the active-object table from the highest index downward and returns
the first index whose class byte is free; when every entry is occupied it
returns index zero as well. The caller reads a returned index of zero as "no
slot available" and abandons that row's grant. Two consequences follow: index
zero of the active-object table can never receive a chest-loot grant even when
it is genuinely free, and rows rolled while the table is full are dropped
silently rather than reported.

The primary pool is evaluated once in the order shown below. A row is eligible
only when its threshold is less than or equal to the chest class. Eligible rows
then roll `1..30` and succeed when the roll is greater than or equal to the
same threshold. Multiple rows can succeed for one chest.

| Order | Result family | Threshold | Quantity or subtype |
|---:|---|---:|---|
| 1 | Food | 7 | Roll `1..2`. |
| 2 | Torches | 7 | Roll `1..2`. |
| 3 | Gems | 15 | Roll `1..2`. |
| 4 | Keys | 9 | Roll `1..2`. |

| 6 | Potion | 17 | Roll `1..8`, then subtract one for subtype `0..7`. |

## 5. Fixed Search Tables

Search has a resident fixed-treasure database separate from the map object
table. The complete public table is `hidden-treasures.md`. It contains 113
records split into parallel semantic columns:

| Column | Meaning |
|---|---|
| Pickup class | The object-name/pickup class staged into the active-object slot and used for the Search narration. |
| Pickup state | The per-record state byte staged with the active-object slot; Get later consumes this as the found-item context. |
| Scene | The town, keep, dungeon, or overworld scene in which the record can match. |
| Floor/depth | The local floor or dungeon depth that must match the party's active Z value. |
| X coordinate | The searched tile's X coordinate. |
| Y coordinate | The searched tile's Y coordinate. |

When Search reaches this table, it compares the searched coordinate and current
scene state to each record in order. On a normal match, the engine checks a
save-backed already-found bitmap. If the record is still clear, the bit is set,
an active-object slot is acquired, the pickup class/state and searched
coordinate are written into that slot, the inventory/status dirty hint is
raised, the staged object is named, and Search succeeds. Repeating the same
Search later skips the already-found record and continues scanning.

Three records in the table have extra gates instead of the ordinary one-shot
bitmap rule:

| Record family | Extra rule |
|---|---|
| Zero-key cache | Requires the party to own no keys and the target tile not to be occupied by an NPC. The gate reads the ordinary Keys counter. |
| Daily cache | Can fire once per in-game day; on success it stores the current day in its cooldown byte, which lives inside the special/quest-item band rather than being a field of its own. |
| Single-use / occupancy-gated cache | Requires no NPC on the searched tile and requires the party to carry none of the item the record grants. The gate reads that item's ordinary equipment-inventory counter, so the grant path never writes it — taking the granted item does. It is not a separate cookie. |

These special cases still use the same final pickup-staging and found-object
narration path once accepted. Implementations should preserve the table's
matching order, already-found bitmap, pickup staging, and special gates rather
than inventing a different hidden-object system.

Before the Moonstone, rare-reagent, and fixed-treasure scans run, surface/town
Search classifies the live tile that was present at the searched coordinate.
For most entries this classification only chooses the location phrase that
precedes any later found-object narration; it does not by itself grant
inventory. Compatible implementations should classify the original live tile
read before the active-object lookup, not any non-treasure active-object class
returned by the coordinate lookup.

| Live tile | Search classification |
|---|---|
| Active object class `0x1F` at the target coordinate | Immediate slot-indexed treasure find through the matching active-object slot; the later live-tile table is skipped. |
| `0x2B` | Location prefix: stump. |
| `0x4E` | Hidden-door find; reveal the live tile and stop. |
| `0x4F` | Location prefix: wall. |
| `0x5A` | Location prefix: shelf. |
| `0x5C..0x5D` | Location prefix: bookshelf. |
| `0xA1` | Location prefix: well. |
| `0xA5` | Location prefix: desk. |
| `0xA6` | Location prefix: barrel. |
| `0xA8` | Location prefix: vanity. |
| `0xAB..0xAC` | Location prefix: under bed. |
| `0xAD` | Location prefix: dresser. |
| `0xAF` | Location prefix: trunk. |
| `0xB2` | Location prefix: brazier. |
| `0xBC` | Location prefix: fireplace. |
| `0xDC` | Generic find prefix; skip the Moonstone scan, then continue with rare-reagent and fixed hidden-treasure scans. |
| Other tiles | Generic find prefix, then continue through Moonstone, rare-reagent, and fixed hidden-treasure scans. |

Search also has a small fixed reagent-harvest table for rare reagents. It
contains three fixed overworld locations:

| Harvest point | Overworld X | Overworld Y | Reagent counter |
|---|---:|---:|---|
| Mandrake point A | 182 | 54 | Mandrake Root |
| Mandrake point B | 97 | 165 | Mandrake Root |
| Nightshade point | 44 | 137 | Nightshade |

A harvest succeeds only when the party searches the matching coordinate at
midnight and the same harvest point has not already been harvested on the
current in-game day. On success, the engine rolls a quantity in the 2..15
range, adds that amount to the corresponding reagent counter with a 99-unit
cap, records the current day as that point's cooldown cookie, and prints the
"sprigs of" reagent narration. Searches at the right coordinate but the wrong
hour, or repeated on the same day, fall through as no harvest.

Each harvest point owns its own cooldown cookie, and the three cookies are
durable save state (`formats/saved-gam.md` Section 10), so the once-per-day
limit survives save and reload. The cookie stores a day-of-month only; nothing
clears it at ordinary midnight, it simply stops matching when the day advances.
The 28-day month rollover does zero all three (`systems/time.md` Section 8).
They start at zero on a new game, which matches no calendar day, so all three
points are harvestable at the first midnight of a fresh game.

Search has a separate trap/detail narrator for per-map object slots that carry
trap-class metadata. The slot metadata has two semantic parts: a trappable bit
and a low difficulty value. Search combines that difficulty with the selected
party member's trap-detection stat family and a uniform `1..30` roll. This
creates a detection bit, not a trap effect:

| Slot metadata | Detection threshold |
|---|---|
| Not marked trappable | `(30 - member trap-detection stat) / 2`. |
| Marked trappable | `(difficulty - member trap-detection stat + 30) / 2`. |

The intermediate threshold is the original unsigned word quantity halved by
one bit, so out-of-range stat or difficulty values should preserve the
wraparound edge behavior rather than clamping before the roll comparison.

The detection bit is set when the roll is greater than or equal to the
threshold. A cleared bit represents a missed or uncertain reading. The visible
result is:

| Condition | Visible result |
|---|---|
| Trappable slot and detection bit clear | No trap. |
| Trappable slot, detection bit set, and difficulty below `10` | Simple trap. |
| Trappable slot, detection bit set, and difficulty above `20` | Complex trap. |
| Trappable slot, detection bit set, and difficulty `10..20` | Generic trap. |
| Non-trappable slot and detection bit set | No trap. |
| Non-trappable slot and detection bit clear | Generic trap false-positive. |

This path is a detection/classification narrator. It does not by itself define
the shared trap effect once a trap is sprung; the damage/status resolver belongs
to `traps.md`. The coordinate probe that reaches this narrator is the active
object lookup described in `systems/active-objects.md`: it returns the topmost
matching object slot's tile/type byte, after which Search owns the feature
narration or pickup-staging branch.

## 6. Dungeon Chest Contents

Dungeon chest contents are generated when the party uses Get while standing on
an already-open dungeon chest cell. The command reads the underfoot dungeon
cell:

| Underfoot cell class | Result |
|---|---|
| Closed chest | Refuses with the must-open-first message. |
| Open chest | Consumes the chest and runs the reward generator. |
| Any other class | Refuses because there is no chest here. |

Consuming the open chest rewrites only the loaded dungeon image for this visit.
The rewrite clears the chest class and preserves the dungeon visit-marker bit,
so an already-looted chest becomes passage-like for the rest of the current
dungeon entry. The on-disk dungeon record is not patched.

The reward generator is table-driven. It iterates seven reward rows in order.
Each row has a gate threshold, a quantity/subtype rule, and an inventory family
to grant when the row succeeds.

For each row, the first roll is uniform in `1..(4 * dungeon_depth + 4)`, where
depth is the current dungeon level index (`0..7`). If the row's threshold is
greater than that roll, the row grants nothing. Otherwise, the row is awarded
and dispatches once through the shared inventory-add path. Multiple rows can
succeed for a single chest, so a chest can grant several item families.

The seven rows are:

| Row | Gate threshold | Quantity or subtype rule | Inventory result |
|---:|---:|---|---|
| 0 | 2 | Roll `1..31`. | Food. |
| 1 | 4 | Use the shared one-based random helper with upper bound `8 * dungeon_depth`. | Gold. |
| 2 | 5 | Roll `1..3`. | Keys. |
| 3 | 10 | Roll `1..3`. | Gems. |
| 4 | 20 | Roll `1..3`. | Torches. |
| 5 | 25 | Roll random subtype `0..7`. | One potion of that subtype. |
| 6 | 25 | Roll random subtype `0..7`. | One spell scroll of that subtype. |

The gold row deliberately passes lower endpoint `1` and upper endpoint
`8 * dungeon_depth` to the shared range helper. At `dungeon_depth == 0`, this
becomes an invalid `1..0` range. If the row's gate succeeds on that level, the
original helper consumes one PRNG advance and then reaches its zero-width
integer-division edge. Compatible implementations should preserve that behavior
rather than silently clamping the bound to one.

## 7. Tile Consumables

Some Get results are not object-table entries:

- **Borrowed objects.** Certain furniture/lit-fixture cells can be "borrowed".
  The cell is rewritten to the open/empty tile, the map redraw hint is set, a
  sound/feedback effect runs, and the party's torch counter is set to 100
  counter units — borrowing a lit fixture is a light source, not an inventory
  item, and it consumes no carried torch. See `systems/lighting.md` for the
  counter's decay. This branch is a tile mutation, not an inventory-add
  dispatch. The traced branch does not debit the shared moral-standing
  selector; crop, table-food, and town-family chest handling own the confirmed
  Get-side standing penalties.
- **Crops.** Crop cells can be picked. The cell changes to the harvested crop
  tile, the party's grain/food-related counter is credited, the shared
  moral-standing selector is debited when nonzero, and a small food
  bookkeeping flag is set.
- **Food on tables.** Specific table-food cells can be eaten only from allowed
  approach directions. A valid reach rewrites the table cell, sets the
  inventory/status refresh hint, credits one food unit, marks the turn as an
  eating action, debits the shared moral-standing selector when it is nonzero,
  and gives eating feedback. An invalid reach refuses because the plate cannot
  be reached and does not mutate the table.

  The two table-food tile variants are directional:

  | Target tile | Successful Get directions | Resulting tile |
  |-------------|---------------------------|----------------|
  | `0x9B` | Only the vertical direction with `dy = -1` | `0x95` |
  | `0x9C` | Vertical directions with `dy = -1` or `dy = +1` | `0x9A` for `dy = -1`, `0x9B` for `dy = +1` |

  Horizontal reaches (`dx = -1` or `dx = +1`) and diagonal reaches are invalid
  for these table-food cells. The command prints the cannot-reach-plate
  feedback and leaves the tile and food counters unchanged.

These are live-map mutations. They should not be written back to the static map
files.

## 8. Inventory-Add Contract

All pickup/container paths converge on an inventory-add dispatcher. Its public
contract is:

- Decode the found-item category or item code.
- Increment the matching shared inventory counter or set the matching quest-item
  flag.
- Clamp or refuse according to that counter's in-game cap where a cap is known.
- Mark inventory/status dirty so the Z-stats and side panels can be refreshed.
- Print the item-result narration for quantities that are visible to the
  player.

Known inventory families reached from pickups and containers are gold, gems,
torches, food/grain, keys, Moonstones, equipment/item categories,
spell-scroll-like results, and special quest/item flags. `catalogs/item-list.md`
is the naming catalog; this spec only defines how pickup results enter that
inventory model.

The found-item class code maps to these public result families:

| Class code | Result family | Inventory effect |
|---:|---|---|
| `0x01` | Must-open-first refusal | Prints the closed-container refusal and does not mark inventory dirty. |
| `0x02` | Gold | Adds the supplied quantity to the party's gold counter, capped at the normal `9999` gold maximum. |
| `0x03` | Potion | Adds one potion of the supplied potion subtype. Potion ids `0..7` follow the colour order in `catalogs/item-list.md`; each colour counter caps at `99`. |
| `0x04` | Scroll or HMS Cape plans | Adds one spell scroll of the supplied spell subtype, capped at `99` per scroll counter, or sets the HMS Cape plans flag when the special plans subtype is supplied. Normal scroll grants use the low three bits of the supplied subtype to select the printed scroll label. |
| `0x05`, `0x06`, `0x09..0x0C` | Equipment | Adds carried equipment stock by the supplied equipment id, capped at `99` per equipment counter. Arrows and Quarrels grant five units per award; other equipment grants add one unit. The canonical equipment id/name table lives in `catalogs/item-list.md`. |
| `0x07` | Key | Adds the supplied key quantity, capped at `99`. Ordinary subtypes add to skeleton keys. Marked odd-key subtypes print odd-key narration, strip the marker bit for the displayed quantity, and add to the skull/special-key counter instead of the ordinary key counter. |
| `0x08` | Gem | Adds the supplied gem quantity. |
| `0x0D` | Torch | Adds the supplied torch quantity, capped at `99`. |
| `0x0E` | Sandalwood Box | Sets the save-backed Sandalwood Box flag used by the endgame. |
| `0x0F` | Food / grain | Adds the supplied food quantity to the food counter. |
| `0x19` | Moonstone | Sets the Moonstone ownership flag for the supplied moonstone slot. |
| `0x1B` | Magic Carpet | Grants the magic-carpet ownership state; one scene-specific acquisition path also raises a quest/event marker. |
| `0xB4` | Shadowlord shard | Sets the Falsehood, Hatred, or Cowardice shard flag for valid shard subtypes `0..2`. |
| `0xB5` | Crown of Lord British | Sets the Crown ownership flag and runs the accompanying regalia acquisition side effects. |
| `0xB6` | Sceptre of Lord British | Sets the Sceptre ownership flag. |
| `0xB7` | Amulet of Lord British | Sets the Amulet-of-Lord-British ownership flag. |
| Other values | No pickup | Prints the nothing-to-get refusal and leaves inventory unchanged. |

For all successful ordinary grants, the dispatcher marks the inventory/status
view dirty and records that the party obtained something this turn. The
must-open-first branch, torches, food, and the Sandalwood Box use custom
epilogues with equivalent user-visible inventory effects rather than the shared
ordinary-grant epilogue.

## 9. Consumed Object Persistence

Inventory changes persist because the shared inventory counters live in
`SAVED.GAM`. Object-table changes persist when they are reflected through the
active-object/object-overlay save path. Live tile-buffer rewrites inside a
location usually do not persist across leaving and re-entering that location.

The visible consumed-object rules are:

- **Per-map object-table pickups.** A successful object-table grant that carries
  an ordinary slot index clears the consumed object's first six record fields in
  the live object table. The last two working bytes are outside this clear
  helper's contract and remain caller-owned scratch. The cleared slot no longer
  matches later Search/Get/Open/Jimmy scans in the current loaded object layer.
- **Surface/town object-table chests.** The chest helper uses the same slot-clear
  path after committing the chest result. Trap and combat chest branches can
  also mark a related combat/effect record as claimed, but the ordinary
  non-combat persistence rule is still "clear the consumed object-table slot."
- **Corpse searches.** A corpse search splits on a single roll before anything
  is narrated, and the fate of the corpse slot follows that split, not the
  narration. The majority arm -- seven outcomes in eight -- **clears the corpse
  slot first**, and only then rolls for what the search is said to have turned
  up. Plague is one rare result inside that already-cleared arm, and the
  several "nothing"-style results are the rest of it, so plague and every
  "nothing"-style narration alike leave the slot cleared and stage neither food
  nor gold. Only the minority arm -- one outcome in eight -- leaves the slot in
  place and rewrites it into a later food/gold pickup; the eventual pickup then
  follows the ordinary object-table grant rule above. *Corrected:* an earlier
  revision had this backwards, attributing the slot clear to the plague outcome
  alone and the rewrite into a pickup to every non-plague search.
- **Corpse-search odds.** Every roll below is over a **closed** range - both
  bounds are attainable - which is the detail most likely to be mis-implemented
  as an exclusive upper bound.

  | Roll | Outcome |
  |---|---|
  | The arm split | **1 in 8** takes the minority arm and stages a pickup; the other **7 in 8** clear the slot. |
  | Inside the minority arm | **1 in 4 food, 3 in 4 gold.** |
  | Inside the cleared arm | Plague on **1 in 32**. |

  An earlier revision of this section gave the contents split as one third
  against two thirds, and the plague chance as one in thirty-one; **both figures
  are withdrawn**. Each was an inclusive/exclusive off-by-one on a closed range.

  The remaining narration in the cleared arm - the several "nothing"-style
  results - is **not uniform**. It is drawn through a chained roll rather than a
  flat four-way choice, which weights it heavily toward the least interesting
  outcome: roughly **52%**, **27%**, **15%** and **6%** across the four messages
  in order. An implementation that picks one of the four with equal probability
  will show the rarest message about twice as often as the original does. This
  is presentation only and stages neither food nor gold.
- **Combat-created body/retrieval slots.** The ordinary post-combat
  trigger-slot reconciler can rewrite a restored `0x2C..0x2F` body-family
  active-object slot into the same broad body/retrieval family consumed by
  Search/Get. Once the player searches or gets that object, the corpse/body
  reward rules above own the food/gold/plague staging; combat itself does not
  grant those contents directly, and combat exit does not grant party gold,
  karma, or a separate victory bonus.
- **Fixed hidden treasures.** Ordinary records are one-shot through the
  save-backed found bitmap described in Section 5. Once the bit is set, later
  searches skip that record even if the temporary active-object staging slot has
  already been cleared.
- **Moonstones.** A found Moonstone is staged as a temporary strange-rock pickup,
  but durable ownership lives in the saved Gate Travel slot. Collecting the
  pickup grants the Moonstone and invalidates the matching saved slot so the
  same buried stone cannot be found again.
- **Live map tile consumables.** Crops, borrowed furniture/table cells, table
  food, hidden-door reveals, and dungeon chest cells persist by rewriting the
  loaded tile buffer, not by clearing an object-table slot. Surface/town tile
  rewrites are visit-local unless another owning system writes the changed map
  image to disk; dungeon chest consumption rewrites the loaded dungeon image
  while preserving the visit marker.

Modern implementations should therefore separate:

- permanent inventory grants;
- persistent object-layer changes, if any;
- visit-local tile rewrites used for feedback and collision;
- static asset data, which remains read-only.
