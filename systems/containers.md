# Containers and Pickups

## 1. Overview

Ultima V has three ways for the party to obtain loose resources during normal
play:

- `G` Get collects visible pickups, dungeon chests, food/crops, and some
  table objects.
- `O` Open opens unlocked doors and containers, including chests that use a
  container helper after the visible tile check.
- `J` Jimmy unlocks locked containers and doors using key stock, then hands
  successful chest cases into the same container/item machinery.
- `S` Search reveals hidden objects, buried Moonstones, traps, and secret
  features; when it finds a hidden object or Moonstone pickup, the discovered
  object is granted through the same inventory-add path used by pickups and
  chests.

This spec centralizes the container and pickup contract. Door state, floor
changes, and the detailed lockpick rules live in `doors-and-z-transitions.md`;
this document owns what happens once a gettable object or container result is
ready to become inventory.

## 2. Runtime Stores

The pickup system bridges three stores:

- **Shared party inventory.** Gold, food, keys, gems, torches, reagents,
  equipment counts, scrolls, and quest items are counters or flags in the save
  image. `catalogs/item-list.md` names the item families; `formats/saved-gam.md`
  gives the byte layout.
- **Per-map object table.** The active map has an object list whose entries
  carry a tile/category byte, position, floor/depth, and inventory-add code.
  Surface and town pickups search this table before falling back to raw tile
  classification.
- **Saved Moonstone slots.** Buried Moonstones are tracked in the Gate Travel
  slot block in `SAVED.GAM`, not in the static map files. Search can surface a
  matching slot as a temporary "strange rock" pickup, and Get invalidates the
  slot when that pickup is collected.
- **Live map tile buffer.** Some pickups are encoded as mutable terrain or
  furniture cells. Collecting crops, borrowing an object, opening a chest, or
  eating from a table rewrites the live tile byte and marks the visible map
  dirty. These mutations are visit-local unless separately persisted by the
  object layer.

Dungeons differ from surface/town maps: a dungeon chest is identified by the
class nibble of the current dungeon cell. The cell does not store its exact
contents. Contents are generated by the command handler when the chest is
opened or gotten.

Search bridges the same stores in a fixed result order. A matching hidden
object-table entry dispatches through the inventory-add path. A matching buried
Moonstone slot creates a temporary strange-rock pickup for a later Get. If both
miss, Search falls back to trap and feature classification: ordinary feature
results are narration, while hidden-door reveal, bomb-trap clearing, chest
post-processing, and treasure-like results can mutate the live tile buffer or
grant inventory through their owning helpers.

## 3. G-Get

Get operates on the tile in front of the party in overworld and town-family
scenes.

1. The command runs the shared tile-interaction preflight gate. A failed gate
   exits without changing inventory.
2. The handler computes the adjacent target coordinate from the current
   position plus the cached direction step.
3. It scans the current map object table for a matching position. In normal
   world scenes, floor/depth must also match. The scan uses a narrow pickup
   filter: a few special category markers and a contiguous loose-object visual
   family are accepted, while actors, blockers, already-handled entries, and
   unrelated object rows at the same coordinate are ignored.
4. On a matching pickup object, the object's inventory-add code is dispatched,
   the appropriate inventory counter or flag is updated, and the object is
   consumed or marked handled according to its object-table entry. Moonstone
   "strange rock" pickups additionally invalidate the associated Gate Travel
   slot after granting the Moonstone.
5. If no object matches, the handler classifies the live map tile. Known tile
   fallbacks include borrowing table/furniture objects, picking crops, and
   eating from reachable table cells. If no fallback applies, Get prints the
   standard nothing-to-get refusal.

Dungeon Get acts on the underfoot dungeon cell. Door cells refuse until opened.
Chest cells roll generated contents and add every successful category to the
party inventory. Other dungeon cells refuse.

## 4. Chests And Containers

Surface/town chests can be reached through Get, Open, Jimmy, or Search depending
on how they are encoded:

- A visible unlocked or closeable container can be opened. The live cell is
  rewritten to the open-container tile, the visible map is marked dirty, and the
  chest helper determines whether the chest is empty, trapped, or grants
  contents.
- A locked container must be Jimmied first. A successful pick rewrites the
  container state and enters the chest/content path. A failed pick can break a
  key and leaves the container locked.
- A too-heavy or otherwise non-openable foreground object refuses before the
  chest helper runs. A non-matching fallthrough can still enter the helper and
  produce a "nothing to open", "can't", trap, empty-chest, or content result
  based on per-map object data.
- A hidden container or object may be found by Search through the map object
  table. Search announces the find and dispatches the object's inventory-add
  code.
- A buried Moonstone may be found by Search through the saved Moonstone slot
  block. Search creates a visible "strange rock" pickup for the matching slot;
  collecting that pickup grants the Moonstone and clears that slot's valid
  destination marker.
- A dungeon chest is an underfoot dungeon cell. Its exact contents are not
  stored in `DUNGEON.DAT`; they are generated at interaction time.

Trap handling is part of the chest helper. A trapped chest prints the trap
result, applies the appropriate damage or effect, and then either grants
contents or leaves the chest consumed according to the helper result. The exact
trap-kind table and difficulty formulas remain open.

## 5. Dungeon Chest Contents

Dungeon chest contents are generated across fixed categories. The decoded notes
identify categories corresponding to gold, gems, torches, food, keys, and a
special/scroll-like result. Each category has its own probability or threshold;
more than one category can succeed for a single chest.

The handler then calls the common inventory-add routine once for each successful
category. For compatibility, an implementation should preserve these rules:

- A chest may grant multiple item families, not just one roll.
- Some quantities scale with dungeon depth.
- The special category has an extra roll beyond the normal category threshold.
- A chest on a door/closed-cell class refuses with the must-open-first message
  rather than rolling contents.

Exact category thresholds, count ranges, and the special result mapping are
deferred until the chest generator table is fully promoted into a public data
spec.

## 6. Tile Consumables

Some Get results are not object-table entries:

- **Borrowed objects.** Certain furniture/table cells can be "borrowed". The
  cell is rewritten to the open/empty tile, the map redraw hint is set, and a
  sound/feedback effect runs. This branch is a tile mutation, not an
  inventory-add dispatch.
- **Crops.** Crop cells can be picked. The cell changes to the harvested crop
  tile, the party's grain/food-related counter is credited, the current food
  gauge is debited when nonzero, and a small food bookkeeping flag is set.
- **Food on tables.** Specific table-food cells can be eaten only from allowed
  approach directions. A valid reach rewrites the table cell, sets the
  inventory/status refresh hint, and gives eating feedback; an invalid reach
  refuses because the plate cannot be reached and does not mutate the table.

These are live-map mutations. They should not be written back to the static map
files.

## 7. Inventory-Add Contract

All pickup/container paths converge on an inventory-add dispatcher. Its public
contract is:

- Decode the found-item category or item code.
- Increment the matching shared inventory counter or set the matching quest-item
  flag.
- Clamp or refuse according to that counter's in-game cap where a cap is known.
- Mark inventory/status dirty so the Z-stats and side panels can be refreshed.
- Print the item-result narration for quantities that are visible to the
  player.

Known inventory families reached from pickups and containers are gold, gems,
torches, food/grain, keys, Moonstones, equipment/item categories,
spell-scroll-like results, and special quest/item flags. `catalogs/item-list.md`
is the naming catalog; this spec only defines how pickup results enter that
inventory model.

## 8. Persistence

Inventory changes persist because the shared inventory counters live in
`SAVED.GAM`. Object-table changes persist only when they are reflected through
the active-object/object-overlay save path. Live tile-buffer rewrites inside a
location usually do not persist across leaving and re-entering that location.

Modern implementations should therefore separate:

- permanent inventory grants;
- persistent object-layer changes, if any;
- visit-local tile rewrites used for feedback and collision;
- static asset data, which remains read-only.

## 10. Open Questions

- **Dungeon chest tables.** Category thresholds, quantity ranges, and the
  special/scroll result need a clean public table.
- **Inventory-add code mapping.** The found-item category byte used by the
  object table is not yet fully mapped to public item IDs. The Get pickup filter
  shape and Moonstone strange-rock path are identified, but many ordinary pickup
  category IDs still need public names.
- **Search trap/feature table.** Surface/town Search distinguishes regular
  treasure, trap tiers, bomb traps, fields, pits, fountains, hidden doors, and
  empty feature descriptions, but the exact trap-kind table and difficulty
  formulas are not yet exposed as a full implementation table.
- **Table-food reach matrix.** The approach-direction rules for the table-food
  cases are known in shape but should be diagrammed against tile art.
- **Persistence of consumed object entries.** Inventory counters persist, but
  the exact object-table clearing/flagging rules after every pickup category
  need a dedicated pass.
